Does the stability weight actually do anything?

A scheduler lets you set a penalty on “how much the roster changes”. When a caregiver calls in sick, does turning that dial up actually buy you a more stable roster?

It depends on what the recovery is allowed to do. If recovery may only place the orphaned visits and must leave every incumbent assignment alone (A1, assignment-only), the number of changed assignments is fixed by the event itself. The dial multiplies a constant. If recovery may also move incumbent visits (A2, displacement) and that genuinely lowers attainable overtime at the same service level, then two or more non-dominated cost vectors exist and the dial really does choose between them.

This page shows that contrast in the paper's data, and ends with the diagnostic the paper proposes: before you expose a stability weight, test whether deviation varies at all over service-equivalent recoveries.

5 · The practical contribution

A diagnostic to run before you expose a stability weight

The paper's recommendation is not a new solver. It is a test you can run on your own instance with the optimiser you already have.

  1. Fix the service level the recovery must hit — the best unserved count both recovery modes can reach.
  2. At that service level, sweep an epsilon-constraint on deviation and record every attainable (deviation, overtime) pair.
  3. Drop the dominated pairs. Count what is left.
  4. If exactly one cost vector remains, a componentwise nondecreasing stability weight cannot change the outcome. Exposing the dial would be misleading: it would look like a control and behave like a constant. Fix the recovery policy instead, or widen the action space.
  5. If two or more remain — which here required displacement to strictly lower attainable overtime at the common service level — the weight is a real control, and the sweep you just ran is also the menu you should be showing the scheduler.
Why A1 collapses. Under the paper's incumbent-feasibility and orphan-placeability conditions, assignment-only recovery can only place orphaned visits into free slots; the set of changed assignments is fixed by the event, so deviation is a counting invariant. A weight multiplying a constant adds the same amount to every candidate, so the service-maximal efficient set holds exactly one cost vector (several assignment vectors may still tie on it). No componentwise nondecreasing scalarization can reveal a second one — a weight cannot create a frontier the feasible set does not contain. Work through a hand-checkable instance →
